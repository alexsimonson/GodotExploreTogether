# What's left from the Unity version — 2026-11-15

What the original Unity project (`E:\claude\_reference\ExploreTogether`, last commit `39e92df`) has that the Godot rebuild doesn't yet, as of phase 5. Written for planning the next round of feature work. For what has already been ported, see the phases in `PLAN.md`.

The core loop is fully ported: maze generation, items, inventory and gear, interaction, the dungeon entrance, the Dungeon Pass and exit, enemies with vision, all three weapon types, health, death and hardcore. What remains falls into three groups:
1. features that worked in the original;
2. features the original only started;
3. things that are intentionally different and shouldn't be ported.

## 1. Worked in the original, not ported yet

### Hub storage
- A chest in the hub (`HubStorage` in the hub prefab, `Storage.cs`), opened with E, that shows a second inventory next to the player's. Items move between them with the same drag-and-drop.
- Saved per character (`hub_storage_inventory` in the character save).
- Open and close animations on the treasure chest model.
- The same script could also show a gear panel, meant for looting bodies. That was never used.
- **Port effort: small.** The inventory UI, drag rules and database tables already exist; storage is another container.

### Resource gathering
- Trees (`TreeResource` prefab, `Resource.cs`) that you hit with the right tool to get items.
- Rules:
  - The equipped weapon must be a tool with the matching role. Roles: Axe, Pickaxe, Shovel, Rake, Screwdriver, Hammer; only the Axe exists as an item.
  - Each hit rolls 0–511 and succeeds on 12–399 (about 76%). Success gives a random item from the resource's list; the tree gives a **Log** (id 432, already in the Godot item catalog).
  - A single-use resource is depleted after one success. Otherwise each success has a 101-in-512 chance (about 20%) to deplete it. The tree is not single-use.
  - A depleted resource shows an "empty" material and comes back after 5 s.
- The Godot Axe already uses interactables when it doesn't hit an enemy, as in the original. Only the resource itself is missing.
- **Port effort: small to medium.** Needs a server-side resource object, replicated per instance like items, plus somewhere to put trees (the hub, or in dungeons).

### Wave Survival mode
A second game mode on its own map (`Arena` prefab, `WaveSurvival.cs`):
- Enemies come from spawn points in rounds:
  - 6 in round 1, then one more each round;
  - at most 10 alive at once;
  - when one dies, another spawns until the round's total is reached.
- Score: 10 per kill and 1,000 per round cleared, shown on the HUD.
- A **Random Box** (`ItemSpawner.cs`) sells a random item (never the Dungeon Pass) for 4,000 score.
- On death it reports: the round you died in, rounds survived, total kills, total score and unspent score. These were only logged, never saved.
- There was an option for killable spawners, turned off.
- **Port effort: medium.** The instance system already supports a new kind of instance. The arena needs geometry, and the art rule in `CLAUDE.md` currently allows only the dungeon art. Multiplayer raises questions the original never had to answer: shared or personal score, and what happens when one player dies.

### Chained dungeons
In the original's Dungeon Crawler mode (`DungeonCrawler.cs`, `ObjectivePanel.cs`):
- reaching the objective offered **Next**, which generated a fresh maze;
- a round counter went up, with a 1,000-point bonus per round;
- the Dungeon Pass's description still says "Allows you to pass to the next dungeon."

In Godot, escaping returns you to the hub.
- **Decision needed:** keep escape-to-hub, or let the group continue into a deeper dungeon (for example bigger mazes or more enemies per level).

### Movement and presentation
- **Crouch:** Left Ctrl toggles it. The collider shrinks by 0.7 m and movement slows to half.
- **Enemy model and animations:** the `ModernMan` model with idle, walk and punch, and a **ragdoll on death** that takes the force of the shot that killed it. Godot uses a placeholder by your choice.
- **First-person arms and held weapons:** an `Arms` model with a slash animation, and weapon models (`deagle`, `sword`, `wand`, `xbow`).
- **Sound:** gunshot and reload sounds (`Resources/Audio`), plus a volume slider in the original's options menu. Godot has no audio yet.
- **Art permission:** these models and sounds are outside `Resources/Prefabs/Dungeon`, the only art `CLAUDE.md` currently allows. Using any of them needs your OK first.

## 2. Started in the original, never finished

These are ideas with some scaffolding, not working features. Porting them means designing them.

- **Skills** (`SkillSystem.cs`, `SkillUI.cs`):
  - 17 skills: Melee, Range, Magic, Health, Stamina, Alchemy, Blacksmithing, Communication, Cooking, Crafting, Engineering, Farming, Fishing, Hunting, Lumberjacking, Mining, Thieving.
  - Levels run 1–100, and each level needs `level × 100` experience.
  - Nothing ever awards experience, and the skills list in the UI is commented out.
  - Resource gathering (Lumberjacking) and combat (Melee, Range, Magic) are the natural first sources of experience.
- **Quests** (`QuestGiver.cs`, `Task.cs`, `Brain.cs`): a quest giver prefab whose interaction is empty, and a task class with a title, description, reward and requirements as plain text. No quest logic exists.
- **Other NPC types** (`NPC.cs`): Zombie, Guard (attacks zombies, one hit for 100) and Citizen (flees from zombies). This script isn't attached to any prefab or scene; `GenericNPC` replaced it for enemies.
- **Stealth** (`StealthSystem.cs`): one calculation that is either 0 or 1/1,500. A placeholder.
- **More magic:**
  - Fire and Earth styles exist as empty methods.
  - Magic areas had a damage-over-time option (`is_dot`: damage every physics tick while an enemy stands inside), but neither wand used it.
- **Secondary action for melee and tools:** it only logged "We should block?".
- **Item fields with no use:**
  - `weight` and `max_stack_size` on every item.
  - The Coin and Health Kit items exist but do nothing. There is no "use item" action.
- **Buildings:** a `House1` prefab, not used anywhere.

## 3. Intentionally different — don't port

| Original | Godot | Why |
|---|---|---|
| A character's save held its in-progress dungeon (maze, items, enemies) and resumed it on load | Dungeons are shared server instances that close when empty | Multiplayer: a run belongs to the group, not one character |
| JSON save files (`FileHandler.cs`) | SQLite on the server | Server authority, safe upgrades |
| Death panel with Restart / Main Menu | Back to the hub (normal) or character select (hardcore) | Fits the hub-based loop |
| Game mode chosen in the main menu | Chosen at the hub's dungeon entrance | Same reason; Wave Survival would get its own entrance |
| `GameEvent` ScriptableObject events | Direct C# events and RPCs | Engine difference |
| Ammo counts stored on the shared item asset | Rounds belong to each gun; spare ammo is an item | Fixed the bug where every pistol shared one count |
| Debug keys (Y lists the inventory, J teleports, H plays an animation) | `--dev-*` command-line options | Testable and headless |

## Suggested order for feature building

1. **Hub storage.** It's the smallest step, reuses what exists, and gives the hub a purpose between runs.
2. **Resources, then skills.**
   - Gathering gives skills their first source of experience, so build them together.
   - Before writing code, decide which of the 17 skills to keep.
   - Settle whether experience lives in the database per skill (a new table and migration).
3. **Decide the run structure:** escape to the hub, or chain into deeper dungeons. This affects scoring, rewards and what Wave Survival looks like next to it.
4. **Wave Survival.** It needs an arena and an answer on co-op scoring.
5. **Presentation:** sound, crouch, enemy and weapon models. Do these once the art direction (and which original assets you can use) is settled.

Quests, other NPC types, stealth and more magic styles are new design work rather than porting. They fit after skills and a decided run structure, since rewards and objectives depend on both.
