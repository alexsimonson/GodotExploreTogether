# Project review — 2026-11-15

A review of the implementation after phase 5 (enemies and combat), written for future reference. When this was written, the latest commit was `f1e9862`. The work after it (the ammo redesign, the pentagram ghost in the player's color, sharing the aim ghost with other players, and doc updates) was not yet committed.

## Summary

It's in good shape. You can log in, pick a character, run a dungeon with others, fight, die and escape, all on a dedicated server. The decisions that are hardest to change later look right. A few things will start to hurt as the game grows.

## What's working well

- **Separate worlds per dungeon.** Each dungeon has its own physics, pathfinding and network visibility, so nothing in one can affect another. Five dungeons were tested at once with no leaks between them.
- **The game rules don't depend on Godot.** The maze, inventory, combat numbers, enemy behavior and saving can all be tested without the engine (106 tests at the time). These rules are where bugs would cost the most.
- **The maze port stayed faithful.** The original generation logic is unchanged. Two separate checks confirm every piece's openings line up: one in the tests and one that raycasts the built geometry in the game (`--dev-check-walls`).
- **Database upgrades are safe.** The server backs up before upgrading, refuses databases newer than its code, and has upgrade tests with sample data (`TempDatabase`). This will matter once real characters exist.
- **The ammo redesign improves on the original.** Rounds belong to a specific gun, and spare ammo is an item. This fixed the original's bug where every pistol shared one count.

## What to watch

1. **Testing in the engine is manual.** The headless multi-client runs catch real bugs, but they are started by hand and judged by reading the logs. Several bugs (players launched into the sky, players invulnerable up close, the vanishing aim ghost) were only caught that way.
   - **Recommendation:** turn a few of these runs into a single smoke-test script that passes or fails. This is the improvement to make first.
2. **The server will slow down as players and dungeons grow.** All dungeons run on one main thread, including physics, enemy AI and navigation baking.
   - Baking a 5×5 maze takes about 40 ms, which is fine.
   - Large mazes, or several dungeons starting at once, could cause noticeable stalls; baking in the background would help.
   - Not urgent for a co-op group.
3. **Each client controls its own movement.** That's fine for friends, but it's why a player can't stand on a teammate's head. Enemies also hit players based on positions that arrive slightly late.
   - If PvP or public servers ever matter, this needs to change.
   - Until then it's a sensible shortcut.
4. **A few pieces will need more structure.** Neither is a problem yet, but both should be tidied before adding hub features like storage, skills and crafting:
   - The server's game code is spread across several large files (`ServerGame.*.cs`).
   - Dev testing options make up a fair share of the client's startup code.
5. **Gaps before hosting outside this PC:**
   - Logins aren't encrypted (ENet without DTLS); see the warning in phase 2 of `PLAN.md`.
   - A hardcore death deletes the character permanently. Marking it as dead instead would allow a graveyard, or undoing a death caused by a bug.
6. ✅ *(fixed 2026-11-16)* **Small mistakes in `PLAN.md`:** it says ".NET 8 SDK" where the project uses .NET 10, and an example path says `/root/Game/...` where the real one is `/root/Main/...`.
